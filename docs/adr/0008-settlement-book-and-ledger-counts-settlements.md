# 8. A settlement is decided in its group's book, and Ledger counts the settlements paid (the Settlements → Ledger link, carried)

## Context

ADR 6 declared the settlement book (`SettlementBook`, T7) and Ledger reading what was settled (`SettledAmounts`, T8).
Request 12 (settle up in cash) is the first feature that records a settlement. Its storm, `settle-in-cash`, decided the
hot spots: no overpayment when two settlements are recorded at once (the book's optimistic check, and the balances
re-read by the second writer); balances counting a settlement as soon as it is recorded (read through a port, never
copied); a settlement recorded by its payee; and a statement that stays the expenses' alone.

Ledger must count the settlements when it reads a balance, so the link Settlements → Ledger (`SettledAmounts`) is now
carried. Ledger's group balances, the suggested settlements (request 11, which reads Ledger's balances through its own
port) and leaving a group (request 9, through Groups' port over the same read model) all count them through that one
read. A member's statement is Ledger's expenses alone and does not change.

## Decision

- **The settlement book is an aggregate per group** (`SettlementBook`, Settlements). Its identity is generated by the
  domain when the book is opened for a group that has none yet (`SettlementBook.open`, version 0). Opening a book
  records no event: a book is a version to compare, not a fact anyone reads. Only `SettlementRecorded` is published.
- **The check is the book's version** (CONC-OPTIMISTIC). The book's row (`settlement_books`, one per group) is inserted
  at version 1 for a group's first settlement, and each later save is an `UPDATE … WHERE version = ?` that moves it on.
  Two writers who read the same version cannot both save: the second gets a `ConcurrencyConflictException`, and the
  command handler re-reads and re-decides in a new transaction, where the first writer's settlement is in the balances.
  Two first settlements race on the insert, which does nothing for the second, and is the same conflict.
- **The decision reads the balances through `IGroupBalances`** (Settlements' port, answered over Ledger's read model),
  in the same transaction as the version. A settlement is refused when it is not a whole number of at least 1, when the
  payer is the payee, when the payer is not a member, or when it is more than the payer owes or more than the payee is
  owed. A refusal changes nothing.
- **Ledger owns `SettledAmounts`** (`ISettledAmounts`, `Ledger/Domain/Expense/Ports`): what each settlement paid moves
  each member's balance by. Its adapter, `SettlementsSettledAmounts` (Ledger's Infrastructure), reads Settlements' read
  model (`ISettlementQueries.paidIn`) and says it in Ledger's words: the payer's balance up by the amount, the payee's
  down by it. `SqliteBalanceQueries` adds these to the expenses' entries at read time, so nothing is copied and a
  balance never misses a settlement that is paid.
- **The composition root and Ledger's wiring build the same stateless read** over the application's file, as ADR 5
  decided for Ledger's balances. Each read model is the same over the same file, so Groups' leaving check and the
  suggestions count settlements too.

## Consequences

- Ledger's balance now includes settlements. The balances still add up to 0: a settlement's two entries net to 0, as an
  expense's do. A statement (request 8) still lists expenses only, so its balance differs from the group's balance by the
  settlements a member paid or received.
- The balance read is two reads (the expenses, then the settlements), outside a transaction it sees a settlement either
  wholly or not at all, and each settlement's entries net to 0, so the sum is 0 in any view.
- A write to a balance is a settlement's, through the book; expenses keep their own aggregate and never contend on it.

## When to revisit

When a provider settlement (request 13 onward) decides its payment through the same book: its pending status will then
count in the balances as paid, a refusal of the provider's webhook will be decided the same way, and the book's version
will serialise both kinds of settlement. Also when a settlement needs to be undone, since a reversal is a settlement's
own fact and is not yet decided.
