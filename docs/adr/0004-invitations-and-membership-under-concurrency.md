# 4. Invitations: an aggregate of their own, and members of a group under optimistic concurrency

## Context

Request 3 (invite by a link, and join) is the third feature. Its storm (`conventions/storms/invite-and-join.yaml`), decided
with the product's owner, puts the invitations in Groups and adds four use cases: `CreateInvitation` and `AcceptInvitation`
(commands answered at once), `GetInvitation` and `GetGroupMembers` (queries). It records two domain events,
`InvitationCreated` and `MemberJoined`, and it links no two contexts. Its three hot spots are decided there: an invitation
is its own aggregate; its id, generated by the domain, is the only proof a joiner needs; and Ledger does not keep a copy of
the members (it will ask Groups, through the port ADR 1 declares as planned).

ADR 3 said which trigger would bring the Group aggregate's concurrency rules in: `several-writers`, the request in which
joining writes the group. It holds now: `CreateGroup` inserts a group, and `AcceptInvitation` writes its membership, so two
commands reach the same `Group`. The triggers, as the binding reads them:

- `several-writers` fires for `Group`: `CONC-OPTIMISTIC` and `DOMAIN-CREATE-VS-RECONSTITUTE` are held there.
- `reacts-to-domain-event` does not fire: nothing in Groups reacts to `InvitationCreated` or `MemberJoined`, so
  `DOMAIN-RECORDS-EVENTS` is not held for them, and the events are not integration events (T3 in ADR 1).

No context and no relationship is added: the Groups and Ledger contexts and the planned link between them are as ADR 1 and
the context map say. The storm's `links` is empty, and nothing in the code carries a relationship it does not declare.

## Decision

- **`Invitation` is an aggregate of Groups** (`Domain/Invitation/Invitation.ts`), extending the building blocks'
  `AggregateRoot`. It is made by `Invitation.issue()`, which generates its id (`Id.generate()`, a random version 4 UUID,
  122 random bits: the link carries it and nothing else) and records `InvitationCreated`. It is read by people who are not
  members, used any number of times and changes nothing of the group, so it is not part of the `Group`. It has
  `fromSnapshot()`, because `AcceptInvitation` loads it, and it is never saved after its creation, so it has one writer and
  no version.
- **The factory is named `issue`, not `create` or `register`.** The storm inventory (clean-ddd 3.2.0) attributes a command
  to every aggregate whose factory the use case text calls by the pattern `X.create(` or `X.register(`, whatever `X` is:
  `Invitation.create(` would be read as `Account.create` (ADR 2) and `Invitation.register(` as `Group.register` (ADR 3),
  and the storm would report the wrong aggregate and events. `DOMAIN-CREATE-VS-RECONSTITUTE` names `create()` and
  `register()` for creation, and holds for a factory where several writers reach the aggregate; `Invitation` has one writer,
  so the rule is not held for it. `issue()` does what the rule asks of a creation that is made once: it generates the
  identity and records the creation event; the caller has checked that the issuer is a member.
- **`MemberJoined` is a domain event of Groups**, recorded by `Group.join()`, carrying the group's id, the account that
  joined and when. It is published after the save, as `GroupCreated` is. Nothing subscribes to it, so it is not an
  integration event. Ledger reads the members when it decides (feature 4), so it needs no copy of them.
- **The membership is part of the `Group` aggregate.** `Group` holds its members in the order they joined; the owner is
  the first, joined when the group was created. `Group.join()` is the one place that keeps each account a member once: it
  answers `AlreadyMember` (a failed Result, `400` through the transport) for an account that is one already, and records
  `MemberJoined` otherwise. This revises ADR 3, which kept the membership as a table the queries read: the invariant the
  storm names (each account is a member once) is a rule of the aggregate, so the aggregate holds the members it is checked
  against. The table remains the store: the read side (`GetGroupMembers`, `GetMyGroups`) reads it.
- **Optimistic concurrency on `Group`** (`CONC-OPTIMISTIC`). A group carries the version it was loaded at (the building
  blocks' `AggregateRoot`); `save()` updates the row only where the stored version is still that one, stores version + 1,
  and otherwise throws `ConcurrencyConflictException`. The Lite use case re-reads and re-decides in a new transaction, up to
  three attempts; the third conflict is the refusal (`409`). A group created is stored at version 1.
- **Joining is `AcceptInvitation`'s one write**: it loads the invitation, loads the group it names, calls `join()` and
  saves the group, all in the request's transaction, and publishes `MemberJoined`. Two different accounts that accept at
  the same time both join; the same account accepting twice is refused the second time, whether the two requests raced or
  not.
- **Who sees what** is as ADR 3 decided it, with the same answer for a group that does not exist: `CreateInvitation` and
  `GetGroupMembers` answer `404` to anyone who is not a member; `GetInvitation` is read by any signed-in person who has
  the link, member or not.
- **Each membership records when it was made** (`expense_group_members.joined_at`). A database created by feature 2 has
  no such column; `GroupsDatabase` adds it on first use and backfills it with the group's creation time, which is the
  only membership feature 2 wrote (the owner's).

## Consequences

- The aggregate and event rules are held by the binding for Groups now, where their triggers fire: `CONC-OPTIMISTIC`
  and `DOMAIN-CREATE-VS-RECONSTITUTE` for `Group`. The tests named in the rules hold them (the version conflict, and
  `fromSnapshot` recording nothing).
- `Invitation`'s factory name departs from the rule's words, for the reason above; a reviewer holds it, and the rule is
  not held by the binding for `Invitation`.
- `AlreadyMember` is `400`, the transport's answer to a rule with no status of its own; the API fragment says only `4xx`.
- The migration is additive and runs once, on the first open of a file. A build older than this one may still write to
  the same file while a deploy is rolling: its owner memberships carry no time, and the store reads such a membership as
  joined when its group was created. Its groups are at version 1 and its writes never change a version, so they load.

## When to revisit

When a context reacts to `MemberJoined` or `InvitationCreated` (then the event becomes an integration event, declared in
`conventions/integration-events.yaml`, and its policy is held by `DOMAIN-RECORDS-EVENTS`), or when the storm inventory
attributes a command to the wrong aggregate for a reason other than the factory names above.
