# 25. An audit of money changes: each context keeps the entries of its own changes, and Ledger reads them through two owned ports

## Context

Request 28 (`api/28-audit.yaml`) lets a member read the group's audit: every change of money, the oldest first, each with who made it (`by`),
when (`at`), what (`action`, about `subjectId`) and how much (`amount`). The changes are the expenses recorded, edited and deleted (Ledger), the
settlements paid and refunded (Settlements), and the balances that passed to the owner when a member left (Groups). An entry is written with its
change, in the same transaction, so a change answered as done has its entry and a refused one has none.

The storm (`conventions/storms/audit.yaml`) was decided before the code. It says no integration event carries an entry (T18): a fact relayed after the
commit would not promise the entry is there when the change is answered. Each context writes its own entries in the transaction of its change, from its
aggregate's facts, and Ledger's audit query reads the other two through ports it owns over their read models. A payment's `by` is the member the change
acts for; a change that records nothing writes nothing.

## Decision

- **No new context and no new relationship.** Two new contracts travel on two relationships the map already declares: `SettlementAudit` on
  Settlements → Ledger (beside `SettledAmounts`, ADR 11), and `PassedBalances` on Groups → Ledger (beside `GroupMembers` and `GroupCurrency`, ADR 5, ADR 16).
  Each is an owned port of Ledger, answered by an adapter over the other context's read model, in Ledger's words (CTX-CONTRACTS). The map is still
  true to the code, and no integration event is added to the published language.
- **Ledger keeps its own entries** in its SQLite file (`ledger_audit_entries`), in the transaction of the change that writes them: a recorded, an edited
  and a deleted expense (`expense-recorded`, `expense-edited`, `expense-deleted`), and the day of a recurring expense (`expense-recorded`, by its payer).
  The entry is a value (`AuditEntry`), its id generated by the domain, its time the clock's. It is never changed, and it stays when its expense is deleted.
  The table is needed because an edit and a deletion lose the amount the expense had.
- **Settlements derives its entries from the statuses they had.** A settlement's `paid` line is written with the fact that paid it (ADR 11, request 19),
  in the same transaction, so a `paid` line exists exactly when the balances started to count the settlement. Its entry is `settlement-paid`, `by` its
  payee when it was recorded in cash and its payer through the provider. A `refunded` line gives `settlement-refunded`, `by` its payee, only when the
  settlement had been `paid`: one refunded while pending was never counted, so it has no entry. A webhook said twice adds no line, so no entry.
- **Groups derives its entries from the passes it keeps.** A leave records its pass (`expense_group_passes`, ADR 16) in the same transaction as the
  leave. The pass has a time, so it is read as the `balance-passed` entry of the member who left, `subjectId` the member, `amount` the balance it left
  with. A zero pass is kept, as the balances count it, and is left out of the audit: the audit has no entry for a balance that passed nothing.
- **`GetGroupAudit`** (`Application/Audit.ts`) is a query of Ledger, answered to a signed-in member (401 to no one, 404 to anyone who is not a
  member). It reads Ledger's own entries (`IAuditEntries`), the settlements' (`ISettlementAudit`) and the passes' (`IPassedBalances`), and puts them
  in the order they were made: a stable sort by `at`, so on the same instant the expenses' own entries come first, then the settlements', then the
  passes'.

## Consequences

- An entry is in the same database transaction as its change, in each context. A crash after the commit keeps both, and a crash before keeps neither.
- Two servers on one database: a settlement's and a pass's entries follow the facts, which are written once (the status line, the pass row). The
  Ledger entry is written in the expense's transaction, which takes turns with the other writers of the file (ADR 17).
- The order across contexts is by `at` (milliseconds). Two entries of different contexts in the same millisecond keep the order the reader lists them
  in, which is not necessarily the order they were made. Within one context the order is exact.
- Adding a change of money later means one entry written with it, in its context, and one more `action` in the public enum.

## When to revisit

When an entry must be exact across contexts within one millisecond (a global sequence would then be needed, and an integration event would carry the
entry instead of the port), when another context needs to read the audit (it would then be a published integration event), or when the audit must be
read for a member who has left the group.
