# Working on tally (guide for AI assistance)

This application is built on the [clean-ddd](https://github.com/jgaNet/clean-ddd) architecture, in TypeScript:
the rules below are generated from [`conventions/architecture.yaml`](conventions/architecture.yaml),
and that file with [`conventions/typescript.yaml`](conventions/typescript.yaml) generates the import rules the linter enforces (ESLint, generated from `architecture.yaml`). Ask the contract before guessing.

## Commands

```bash
yarn check:conventions   # the contract is sound, the documents are rendered from it
yarn check:conventions   # the language's own check, as CI runs it
yarn format:check        # the language's own check, as CI runs it
yarn lint                # the language's own check, as CI runs it
yarn typecheck           # the language's own check, as CI runs it
yarn test:units          # the language's own check, as CI runs it
yarn test:e2e            # the language's own check, as CI runs it
yarn architecture inspect | rules | concepts | verbs | checklists
yarn architecture rule <ID> | concept <id> | verb <intent> | checklist <kind> | place <kind>
yarn architecture plan validate|explain <file>        # a change, stated before it is written
yarn architecture mode feature|architecture           # which rules this change is held to
```

## The rules (enforced)

<!-- generated from conventions/architecture.yaml (rules); edit the YAML, then run the conventions check with --write -->
- A relative import names a sibling file and nothing else; anything across directories goes through the path the import rules are written against. *(ARCH-RELATIVE; linter)*
- Dependencies point inward and contexts stay apart — each file imports only what its row of the dependency table allows; there is no exception and none may be added. *(ARCH-INWARD; linter)*
- The building blocks import nothing outside themselves, not even the shared kernel; the shared kernel imports the building blocks and no context. *(ARCH-TREES; linter)*
- Every directory under the contexts tree is a context declared in the language's binding, holds only the declared layers and its wiring file. *(ARCH-CONTEXT-DECLARED; check)*
- A context's wiring is one file building a Module as data — its name, its commands, its queries, its domain event and integration event handlers; anything else it exposes is a named export of that file. No container, no builder, no service locator. *(ARCH-MODULES-DATA; review)*
- A command has exactly one handler — the Module lists it once, with one handler, and every command a route or a policy builds is one the Module lists; a fact may have any number of subscribers. *(ARCH-ONE-HANDLER; check)*
- ExecutionContext carries what exists per request and nothing else — who is calling, the trace, the transaction, the bus, the logger. A mailer, a clock, a model client is a constructor dependency of the handler that needs it. *(ARCH-EXECUTION-CONTEXT; review)*
- A refused command or query is a failed Result value, never a thrown exception; throwing (or panicking) is for programming errors and corrupted state only. *(DOMAIN-RESULT; tests)*
- Only an aggregate root records domain events (`record(...)` inside a behaviour); handlers never construct one, they call `publishDomainEvents(aggregate, context)` after saving. *(DOMAIN-RECORDS-EVENTS; types)*
- `create()` / `register()` validates and records a creation event; `fromSnapshot()` records nothing and throws on corrupted data. *(DOMAIN-CREATE-VS-RECONSTITUTE; tests)*
- An aggregate generates its own identity (`Id.generate()` in `create()`). A repository loads and saves aggregates, and answers the facts a domain rule needs about the collection (`findByEmail`, `countByOwner`); it never hands out identities and never searches for a screen. Identity is born once — a thing first made in one context and taken up by another keeps the id it was born with; the integration event that announces it carries that id, and the receiving side builds its object on it instead of generating a new one, so the id a client was answered finds the thing in every context. *(DOMAIN-IDENTITY; review)*
- Time comes from the one clock the wiring passes (DOMAIN-ONE-CLOCK); identity is generated by the domain; anything else that is not a function of the business state (randomness, a model, a person, another system) lives behind a port named for what it decides, and its result is a plain value the aggregate validates and may refuse. *(DOMAIN-NON-DETERMINISM; review)*
- An application has one now: a clock the wiring builds and passes to whatever decides or records a time — a command handler, an event handler, a job, an adapter, the bus — and that hands it to the domain as a parameter, always given; a domain method's time parameter has no default, and nothing but the building blocks' system clock reads the machine's time. *(DOMAIN-ONE-CLOCK; linter)*
- Domain events are made durable with the state they describe, in the same transaction (the outbox), and published from there after the commit — never before, and never from memory alone; a rolled-back transaction stores nothing and leaves the events on the aggregate; a fact a crash kept from being published is published on the next relay, so a subscriber may see a fact twice and the bus delivers a message it already delivered once only; a reaction runs in a transaction of its own, and what it saves and what it publishes are made durable and published the same way. *(EVENT-AFTER-COMMIT; tests)*
- Queries return read models, repositories return aggregates; never the other way. *(QUERY-READ-MODELS; types)*
- Contexts talk in two ways only — integration events published in the shared kernel, and ports the asking side owns, answered by an adapter over the other context's read model; a context's Domain never imports another context. *(CTX-CONTRACTS; linter)*
- An aggregate carries the version it was read at and never changes it; `save()` stores version + 1 and refuses an aggregate that is no longer at the stored version with a ConcurrencyConflictException; the command handler then re-reads and re-decides in a new transaction, up to three attempts, and the third conflict is the operation's refusal. *(CONC-OPTIMISTIC; tests)*
- Every file the concept map names exists, every documentation link resolves, nothing silences the linter, and the generated import rules refuse and allow what the probes say. *(ARCH-MAP-IS-REAL; check)*
- Every language answers the same HTTP API — the same routes, status codes, body shapes and public names — so one black-box scenario, run against each server, passes unchanged; the public name of an operation is its intent or its fact without the suffix of its kind (`ShareNote`, `NoteShared`). *(API-ONE-SURFACE; tests)*
- A command's request body is refused by the transport for its shape only — a field missing or of the wrong type answers 400; whether a value is allowed (one of a list, a format, a length, a range, a count) is the domain's to decide, and its refusal is the operation's ERROR behind the 202, named by the rule's exception. *(API-BODY-SHAPE; tests)*
- A command whose outcome is read later (answered 202 with an operation) needs a signed-in caller unless its handler says, once, that anyone may ask for it, and so does a use case of a profile that answers every command at once unless its definition says so; the transport refuses a missing caller at once with 401, before anything is published or run, in the one helper every such route calls. A query that needs a caller and has none answers 401 too, 403 is for a signed-in caller the rule refuses, and any other command answered at once keeps its own 4xx; the handler still asks for its caller's id and the aggregate, or the decision, still decides what that caller may do. *(API-CALLER-AT-TRANSPORT; tests)*
- Every relationship between two contexts is declared once in the context map, with the strategic pattern it follows, the mechanism that carries it and why; the contracts it carries are read from the code, and the check refuses a link in the code the map does not declare and a declared relationship nothing in the code carries, unless it is declared `planned` — decided before the code that carries it. *(CTX-MAP-DECLARED; check)*
- Every integration event is declared once in the published language, with the context that publishes it, the thing it announces when it announces one, and the payload of each version it was published in; every language's code carries the last version, field for field, and the check holds each inventory to it; a version once merged is changed only by an added optional field — a field removed, renamed or retyped is a new version, and the gate refuses the change in place; an event that announces a thing carries the id it was born with. *(CTX-PUBLISHED-LANGUAGE; check)*

Why each rule holds and how to fix a breach: `architecture rule <ID>`; the linter or the check that refuses one says it too.

## How to add a feature

Every context here is held to the Lite profile (`default_profile` in the binding): `yarn architecture profiles` says
which rules it holds, which it holds where a trigger fires, and what a trigger brings in — an aggregate,
a domain event, a command answered later come in by an ADR, never quietly.

Run `yarn architecture checklist <kind>` for the file list, and `yarn architecture verb <intent>`
for the route; both answer for the profile. In short: the domain first — a decision in
`<Thing>.decision.ts`, a pure function of the state, the command and the time that answers the new state
and its facts or the refusal (no port, no `async`, no clock: the linter refuses them there) — then the use
case, a function of its ports in the file of its thing's use cases that loads, decides, saves and
publishes, then the store's adapter only if a method changed, then the route, which answers it at once
through `answerAtOnce()` (`401` to a missing caller unless the use case says `{ caller: 'anyone' }`),
then the use case listed in the `LiteModule` of `module.local.ts`. Expected failures are `Result` values,
never thrown.

## The API's shape

A request's API goes into `api/` as a fragment first, before the code (`api/README.md`); the end-to-end
tests hold every answer to it, through `apiClient()`. *(API-ONE-SURFACE; tests)*

When a specification (a request, a ticket, an API document) says what the API answers — a field, its type, when
it is `null`, a status — that is the shape, even where the code already answers otherwise: change the code that
projects the answer (the read model, its projection, the route's schema) and the tests that read the old shape,
never the specification. A field is `null` only where a specification says so; a state added later keeps the
values the earlier ones gave. What an operation answers when it is read is the contract's (`http.operation`); a
specification that wants another shape says so where it is first decided. *(API-ONE-SURFACE; review)*

## Things to avoid

- A generic `Mapper`, `Repository<T>`, `Saga`, service locator or DI container. *(ARCH-MODULES-DATA; review)*
- Fixing a boundary violation by silencing the linter instead of a port: the conventions check refuses one. *(ARCH-MAP-IS-REAL; check)*
- Changing anything under `src/Architecture`, `src/SharedKernel` or `conventions` while adding a feature:
  `yarn architecture mode feature` will say so, and that is a finding, not a detour. *(the feature mode; check)*
